# 歌曲和歌词 → 可用 MV

## 1. 接收与对齐

使用 `prepare_project.py --audio <实际文件> --lyrics <UTF-8歌词> --out <新版本目录>`。若 ffmpeg 不在 PATH，显式传 `--ffmpeg` 和 `--ffprobe`，本机路径见 local-runtime-and-publish.md。该脚本只准备媒体，不等于视频生成。

保留原歌词 `lyrics.txt`。另写 `transcript.txt`，一行一个实际演唱短句；去掉非演唱的段落标题与导演说明，保留真实重复段。不要先验删掉歌词中的对白或 AI 字样。

运行本地对齐：`<含mlx_audio的python> scripts/align_lyrics.py --project <目录> --model <模型目录> --transcript <transcript.txt>`。得到 `alignment.raw.json`、`cues.json`、`lyrics.srt`。这是机器草案：核对快唱、拖音、重复、漏唱和歌曲尾部；返回文本与歌词不一致时脚本保留原始结果并失败，不猜字数平均时间。

长歌或低置信区域可切片重新对齐，但必须把切片偏移还原到源时钟。零长词、不合理跨段或强制对齐成功都不证明唱对。需要时使用实际转写/听音；无法听审就在记录与交付中说明。

检查尾部能量、静音区间与实际语音。对用户指出的附加口播可用片段强制对齐定位。确定口播和歌曲分离后，优先在音乐自然衰减后剪去附加尾段；若叠在音乐上，不能声称简单裁尾无损，需局部编辑并检查听感。保存 `edits.json` 的 source_in/source_out、时间映射、理由，必要时同步字幕。不要对所有歌固定截断 5 秒。

## 2. 编排画面

先选择视觉表达，再准备素材。根据用户 2026-11-11 提供的参考，当前这类 AI 歌曲优先考虑**动态歌词＋图形隐喻／界面事件**，或少量贴纸参与的轻量拼贴。文字、按钮、路径、计数器也能作为动作主体；没有人物不妨碍做成动画。具体路由和参考段落见 [轻量 MV：参考与表达方法](lightweight-mv-references.md)。

角色故事仍是可选分支，适合人物关系和反应确实承载剧情的歌，或继续修改已认可的角色作品；此时读 [主线任务：动画与剪辑经验](main-quest-lessons.md)。不要因过去采用过人物就先造角色图集，也不要把“文字多”直接等同于“信息讲解”。判断画面是否在发生事件，而不是仅换一张解释卡。

按实际短句和间奏写分镜：`start / settled / cue / hold_end / end / focus / action / resolved_state`，使用角色时附 `character_id`。以整帧和半开区间构建时间轴。先明确观众在这一刻看懂什么；不是每秒都必须切镜头。图形路线直接写对象的前后状态，不为填写角色字段额外造人。

- 开头在前奏内交代一个具体冲突或悬念。
- 主歌逐步演出事件；对象在前后镜头保持身份。
- 副歌让重复有升级，避免几遍只有同一张大字卡。
- 间奏继续动作、反应或转场；不要把尾部全部当无事可做的空页面。
- 结尾让视觉落在歌曲的最后一个情绪点，必要时提前片尾画面配合剪辑。

选一种主视觉语法贯穿全片，按段落变奏；界面闹剧、角色故事、实景素材、拼贴、动态歌词都可以，蓝按钮不是统一皮肤。图形与文字能直接完成的镜头直接绘制；只有画面确实需要时才生成或获取角色、背景等位图素材。文字和字幕由程序绘制以保证可读性。已有可用 motion-graphics、captions、video-editing 或 imagegen 技能时，只读取本次确实用到的部分；没有这些技能也可用 Python/Pillow/FFmpeg 和可用素材完成，不把生成某类素材的工具缺失说成整个任务不可能。

本机可用的渲染路线为 Python/Pillow → FFmpeg；源码随片交付。不要用 Python 几何图形临时拼一个复杂人物替代合适素材。

### 轻量优化顺序与制作边界

- 在用户认可版上修改，保留已选歌曲、歌词时钟、人物身份和画风。只调画面时不重新生成音乐或重做对齐。
- 按“事件出现 → 后果可见 → 停顿／反应”组织节奏。角色路线可用“动作／屏幕特写 → 人物反应 → 回到全景”；图形路线可用“对象改变 → 局部揭晓 → 留白”。切镜要有叙事原因，不机械地每拍切一次。
- 喊停、打断之前留短暂蓄势；笑点用“结果揭晓 → 愣住 → 反应”形成节奏。停顿从歌曲和台词空隙中安排，不剪断或拉伸歌曲。案例的约 0.65 秒仅是参考，不套成固定规则。
- 姿势素材切换可以安排在切镜点，配合小幅进入与落定；减少持续抖动、弹跳和无目的推拉。多张静态表情、整体位移或摇晃不等于连续肢体动画，不据此承诺自然动作。
- 近景优先使用现有场景／界面原始图层重新构图，避免把杯子、前景道具或别的角色裁成残片。镜头重构图之后再绘制歌词，字幕不随画面缩放或裁切。
- 不采用复杂骨骼、关节绑定、IK 或自建角色动画系统，也不为几个动作自动推进新订阅。现成视频生成工具若可用，可按已授权范围补少数关键连续动作片段；明确额度不足时停止重复提交，保留原因和素材，回到现有素材与剪辑优化。有不可替代的生成需求时，明确说明实际缺项。
- 用户认为制作过重时，立即收回到已认可版本及当前修改目标，保留实验但不继续扩建。交付可观看的新成片，而不是把实验预览当成已解决动作问题。


## 3. 角色和元素必须有来由

使用人物、品牌化身或需要绑定身份的图标时写 `cast.json`，例如：

```json
{"characters":[{"id":"claude","name":"Claude"}],
 "assets":[{"path":"pet.png","represents":"claude"}],
 "bindings":[{"scene":"chat","character_id":"claude","asset":"pet.png","display_name":"Claude"}]}
```

绘制窗口名称与角色资产时使用同一记录。`check_video.py --cast cast.json` 会发现表内身份冲突；它不能识别画面里是否实际用了另一张图，所以还要看渲染后镜头。案例 renderer 的简化 assistant/mascot 表也受支持。

纯文字／普通图形路线不要求角色图集或 `cast.json`；在分镜中保持对象身份即可，检查命令省略 `--cast`。出现多个品牌时仍需看清名称与元素的归属，不因省略角色素材而省略逻辑核对。

图标应执行动作、标识真实功能或表现反应。一个悬在角落的品牌药丸、没有动作目标的 Agent 节点网、一直弹跳的宠物，不能仅因为“科技感”就加入。用特写、全景、对象移动与反应镜头丰富画面；避免同时增加大字、卡片和角色动作争抢注意。

## 4. 渲染与检查

默认沿用已选版式；未指定时可用 16:9、1920×1080、30fps。纵版需重排版，不能简单裁横版。音乐为主音轨，不额外配旁白盖住歌词。

一次集中检查：代表帧看构图和字形；连续动作帧/正常速度预览看节奏、遮挡与因果；听音核对歌词、转场和收尾。修复发现的问题，再检查受影响片段。不要为主观“再精美一点”无限重做。

`check_video.py --video final.mp4 --out qa.json --expected-duration <秒> --cues cues.json --cast cast.json` 完整解码并检查时长、音画差与句区间。若只是保留源音轨前 N 秒，可加 `--source-audio <原音频>` 检查前 N 秒相关性。包含中间剪辑或混音时不适用这个简单比较，需按 edits.json 单独检查。

记录哪些是技术检查、画面抽查、实际听审；不能用“解码成功”宣称听感已验收。

## 5. 交付与复用

封面按 [剧情封面](story-covers.md) 单独构图：沿用片中的视觉语言，把歌曲的核心矛盾浓缩成一个动作或图形关系；角色不是封面的必要条件。

交付真实 MP4、封面、完整 SRT、分镜总览、项目/剪辑记录、适用时的角色表、可再运行源码及素材、qa.json。文件名带版本，保留之前尝试。动态歌词已经完整可读时可直接承担歌词呈现，不再强行叠一条重复字幕；仍保留完整 SRT 用于编辑。

修改时先定位反馈对应的对象、时间或角色，在认可版本上更改；不无故换歌、改词或重设计整片。只要求做视频时不投稿。只要求存 skill 时不生成歌曲、不上传、不创建栏目。
