# 《只想要个蓝按钮》：跑通的过程与边界

## 已认可的结果

用户提供 Mureka 歌曲与已确认歌词，制作横版 1080p、30fps 的动态界面喜剧。核心冲突：只要求按钮变蓝，Agent 却把首页拆了。最终版 69 秒，使用 Claude 名称与其橙色像素宠物。保留原歌曲自然收尾，剪掉之后独立追加的口播。2026-11-10 通过项目队列提交 B 站，回执 BV1kJW36aEWq。

案例源码与素材见 [随附示例](../assets/blue-button-example/)。
成片可在 [B 站观看](https://www.bilibili.com/video/BV1kJW36aEWq/)。

用户认可的是故事表达和制作方法，不是把所有新歌曲套进程序员吐槽模板。

## 修正过的问题

| 问题 | 实际修正 | 下次的动作 |
|---|---|---|
| Gemini 成歌与给定歌词对不上 | 用户放弃该音频，改用 Mureka 版本 | 对齐采用的实际文件；不把强制对齐结果当成演唱正确证明 |
| 页面显示时长与下载文件不同 | 下载文件解码约 73.974 秒 | 保存文件 SHA256 与实测时长；不沿用另一候选的 48/69 秒 |
| ChatGPT / AI 标签悬浮且突兀 | 名称放进真正的聊天窗口，Agent 标签跟随操作光标 | 新元素有具体身份或叙事用途 |
| 画面单调，副歌都是大字 | 菜单被宠物拖走、登录逃跑、撤销越撤越乱、两个 Agent 争抢 | 重复歌词安排递进动作；近景让因果看得见 |
| ChatGPT 名称和 Claude 宠物混用 | 统一为 Claude，从 cast.json 读取名称与宠物归属 | 先做角色表，再审实际镜头；不能只对表做检查 |
| 结尾有“当前内容由 AI 生成” | 对齐定位 70.92–72.92s；音乐约 68.6s 已衰减，输出截到 69s | 检查每首歌的尾部，区别歌词、音乐与独立追加语音 |
| 剪尾后原片尾在 70s 才出现 | 片尾改到 67–69s；前一个反应镜头同步缩短 | 音频剪辑后更新视觉时间轴，不能只砍文件 |
| 字体视觉不够统一 | 采用 Hiragino Sans GB W6、统一颜色与 UI 字号 | 检查实际渲染中文，不只检查文件存在 |
| 技术检查容易被当完整审片 | QA 分列解码、音轨相关性、抽帧与未听审 | 如实报告范围，正常播放/听音能力可用时补足 |

## 打包案例的使用方式

`assets/blue-button-example/` 包含最终渲染源码、宠物、cues、cast、歌词和场景记录；不包含用户 MP3、字体、模型、账号凭证或成片。宠物来自用户提供的 Claude 终端截图的透明衍生图，只代表该角色，不自动挪用为别的品牌。

在一个新目录用 prepare_project.py 处理本次实际采用的原 MP3（SHA256 `3266cd002f70d2095e72c61be51b27220bccc6170196ff9954ac65cba1c894e7`），然后复制案例资产进去，保持源音频名 `song.mp3`。设置 `FFMPEG_BIN` 指向本机 ffmpeg，运行 `python3 render_mv.py`。依赖 Pillow、numpy、soundfile 与上述 macOS 字体。

这个脚本保留本曲真实时间点与 69 秒剪辑；原音频换了就不能沿用。新作品只借用 pane、text、component、cursor、pet、FFmpeg 管道等实现经验，重写 draw()、分镜、角色与时间轴。不得把该渲染器标成适配任意 MP3 的自动模板。

案例首次确认了句级对齐与实际图像效果，但没有逐句人工听审。技术复验可以重复，仍不能自动升级这个历史听审状态。

## Skill 安装时复验

配套脚本实际读取原 MP3、运行本地对齐得到 12 句，并由打包源码重新生成了 69 秒 MP4，其 SHA256 与最终交付完全一致。角色冲突、字幕越界、对齐文本错配和重复准备覆盖保护都已实测。详见 [验证记录](../references/validation.json)。未重新调用 Mureka 或再次投稿，未改变人工听审状态。
